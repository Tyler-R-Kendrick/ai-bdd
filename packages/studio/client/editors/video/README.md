# Video composition workflow

The dedicated editor uses frame-aligned clips on named tracks. Clips can carry image, video, audio, text, shapes, and bounded geometric paths. Persisted first-generation layer compositions normalize without dropping their identifiers, typography, appearance, or large layer stacks. Each video remains an artifact with its own conversation, ADR, and immutable content revisions.

Use **Import media** for authenticated image/video/audio uploads, select a clip to edit source-in, start, duration, placement, gain, and opacity, and split at the playhead. Drag clip bodies to move; drag the ends to trim. Trimming and splitting retain source and animation offsets, so nonlinear animation continues through the cut. Locked clips remain selectable but cannot be edited. Undo/redo retain the last fifty edit snapshots. Text can use built-in faces, uploaded WOFF2 files, or retained editable font designs from brand compositions. SRT and WebVTT captions become editable timed text clips.

Keyframes interpolate position, scale, rotation, opacity, and audio gain at exact composition times. The player clock controls interactive playback; saved render frame positions come from frame number divided by frame rate. A conflicting remote revision retains the local draft and offers a draft download before loading the new revision. Viewer controls prevent modification.

**Render MP4** and **WebM** render the saved artifact revision through the authenticated worker API. The CPU driver captures generated, application-owned DOM at exact frame positions and encodes the frames with FFmpeg. It never executes uploaded HTML/JavaScript, permits only project-owned assets, blocks capture-page network requests, and admits only file/pipe FFmpeg inputs. The encoder mixes actual trimmed source audio and gain automation, then independently checks output streams and duration with ffprobe. Repeated identical local fixture renders are compared byte for byte. That observation does not assert identical encoding across different browser/FFmpeg/font versions.

Render snapshots, metadata, and completed output files persist in the configured SQL/ObjectStore adapters. Queue deliveries contain only a durable job ID. A worker restart or duplicate delivery resumes through the shared fenced job coordinator, without relying on the original HTTP response process. Publication rechecks membership, artifact revision, and cumulative project quota inside the output transaction. Queue size, concurrency, total source bytes, decoded media pixels, render pixels, time, and output bytes are bounded; a failed or cancelled render never becomes a completed output. A source's declared duration does not override the decoded file's actual duration.

`server/video-renderer.ts` exposes `VideoRenderDriver` and `RenderOptions`: immutable composition/title, authorized asset bytes and MIME, format, cancellation signal, progress callback, and the validated output bytes. The included Chromium/FFmpeg driver requires a long-lived worker. `server/video.ts` registers the `video.render` handler with the provider-neutral `DurableJobRuntime`. Admission, immutable source snapshot, and outbox intent commit atomically before external dispatch. The worker materializes hash-checked project assets, stages a fence-specific immutable output, and publishes file metadata/quota/audit/result under the coordinator's final idempotent SQL commit. Completed redeliveries do not repeat rendering or publication; stale attempts cannot overwrite another worker's output. Object-storage staging happens outside SQL locks, with durable cleanup intents for failed attempts. Hosting maintenance calls `cleanupStaged()` alongside coordinator recovery. A serverless function does not assume an in-memory queue, Chrome, FFmpeg, or its response lifecycle provides a durable worker; the configured queue consumer executes the registered worker handler.

**HyperFrames ZIP** exports documented composition/clip data attributes, local media/fonts, an editable `studio.json`, and a native timeline adapter registered in `window.__timelines`. The adapter implements the actual HyperFrames direct-timeline contract: duration/time/seek/play/pause, plus compatible totalTime/progress helpers. It bundles no GSAP. HyperFrames owns the playback/capture clock; Studio's adapter applies the requested frame time. Importing the archive reads only the bounded manifest and media; it never evaluates the composition's HTML or scripts. Media are uploaded again under the destination artifact's project before references are replaced. A plain project JSON download is suitable for restoring into the same project, where its authenticated asset references remain available.

HyperFrames interchange preserves editable Studio keyframes and audio automation in the manifest. The producer HTML's media volume attributes carry base clip gain; automated gain stays in Studio's renderer/manifest. HyperFrames CLI 0.8.217 was exercised against a generated native-adapter fixture: lint, browser validation, and layout inspection each reported zero errors/warnings, and strict rendering produced an H.264 320×180, 24-frame, one-second MP4 with changing frame hashes. These are specific executable compatibility observations, not a claim about every future HyperFrames version or proprietary Studio capability.
