# Literal code edit contract

Model-backed code proposals use bounded literal replace, create and delete operations against the selected saved artifact. Existing-file choices come from that artifact's filenames. The independent reconstruction guard validates every operation's schema, original-file scope, conflicts, count and aggregate text bounds before applying any operation. Paths are never stripped or normalized into another target.

A validated replacement whose `find` and `replacement` strings are identical is an identity operation: it leaves every source string unchanged, whether or not that nonempty literal occurs. Reconstruction skips only that operation after the validation pass. Identity operations still count towards request bounds and participate in path/conflict checks. Effective replacements still require an exact existing literal, and the final project must change a file or its entry. An identity-only or net-unchanged proposal is refused.

Models remain instructed to omit redundant operations and preserve unrelated bytes. The identity rule changes deterministic reconstruction, not weights, resource budgets or the expected requested result. It does not rewrite effectful edits or accept invalid paths.

Code generation now permits at most two complete proposal rounds within one user job, using one captured harness/provider/model. Only typed mechanical missing-literal or conflicting-operation errors permit the second round. A no-change plan, invalid cached typed plan or other known patch-reconstruction failure is terminal. Provider refusals, SDK schema failures, resource failures, cancellation and authorization/source changes retain their existing error classification and do not enter repair. The original request and frozen source are retained. A repair uses ordinary typed user/assistant/user history: original request, bounded untrusted previous plan text, then trusted static validation feedback with an operation index and optional original scoped filename. No edit is unescaped, normalized or rewritten by this workflow.

Each round has a distinct durable raw-plan receipt and model/header/native idempotency key. Raw plans are validated again when replayed, and the selected plan is reconstructed again before publication. The outer `model-output-code-patch-v4` step isolates earlier full-content and patch receipts. Authorization, cancellation, ownership and source-version fences run before each round and publication. The first invalid plan is not published, exhaustion fails safely without another complete round, and canonical source changes only through normal owner acceptance.

Each round retains the existing six-step SDK tool bound and authorized read-only tools. Two proposal rounds therefore do not imply two physical provider calls when tools are used. Existing provider/delivery behavior before a durable receipt commits remains at-least-once; stable keys do not establish universal provider deduplication. The 120-second whole-request signal, model limits and all semantic acceptance checks remain in force. Earlier rejected assessments retain their original source and result; controlled workflow checks are not a new weighted authoring qualification.
