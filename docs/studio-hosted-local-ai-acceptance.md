# Hosted local-model acceptance

This procedure verifies an explicitly approved Ready deployment using downloaded, pinned local weights. The protocol itself is not evidence of a successful hosted inference run. Its guards are offline tests; actual HTTP and screenshot receipts are generated only when the operator runs it with explicit write and usage opt-ins.

The HTTP protocol is `packages/studio/verification/hosted-local-ai-live.mjs`. It accepts only an approved project preview hostname or the exact canonical production origin. Production additionally requires its separate production-write opt-in and never receives the preview identity header. Requests remain on that exact origin, redirects are manual, credentials stay in memory, and the sanitized progress file is persisted atomically. Do not run before the release lead confirms the reviewed source/deployment Ready.

Required operator configuration uses references, not credential values in command arguments:

- `STUDIO_HOSTED_LOCAL_AI_ORIGIN`, `STUDIO_HOSTED_LOCAL_AI_SOURCE` (full commit SHA), and `STUDIO_HOSTED_LOCAL_AI_DEPLOYMENT_ID` identify the reviewed deployment.
- `STUDIO_HOSTED_LOCAL_AI_ALLOW_USAGE=1` and `STUDIO_HOSTED_LOCAL_AI_ALLOW_WRITE=1` authorize one bounded synthetic workflow. The exact canonical production target also requires `STUDIO_HOSTED_LOCAL_AI_ALLOW_PRODUCTION_WRITE=1`.
- `STUDIO_HOSTED_LOCAL_AI_EMAIL`, `STUDIO_HOSTED_LOCAL_AI_GITHUB_SESSIONS_FILE` and a fresh `STUDIO_HOSTED_LOCAL_AI_REPORT` identify the expected account, explicitly selected private browser-cookie export, and private receipt destination. The session file follows the [hosted platform acceptance format](studio-hosted-acceptance.md) and contains exactly two distinct sessions obtained through the configured GitHub sign-in adapter; password-file inputs are refused. Preview access additionally uses the environment's protected `VERCEL_OIDC_TOKEN`; it is never printed.

The protocol creates a fresh synthetic project through the SQL-only project route, then checks both catalogs before any source/message/inference action. It rejects every configured Gateway, external provider or unapproved model, even if the selected chat profile is local. It requires default `t3-code / studioLocal / studio-local/qwen2.5-0.5b-instruct-q4-k-m`, the explicit local CPU alternative, and an independent `llama-cpp-cpu` decision profile. The allowlist pins the Qwen 0.5B and SmolLM2 135M GGUF hashes; unknown aliases require another reviewed guard update.

The synthetic passage specifies a tiny calculator with observable `2 + 2 → 4` behavior. Title generation and automatic chat participation stay manual. A separate decision-profile persistence check raises the threshold to 0.71, reloads it while confirming the generative profile stayed unchanged, then restores the normal 0.7 before classification. It never lowers the quality gate to manufacture acceptance.

One retained human question requests `2 + 2`; one explicit native T3 chat job must produce an actual assistant answer `4` in that artifact thread. The existing selected-passage design-review workflow then exercises native predicates, a finite harness choice and an ordinal score. No unrestricted classifier endpoint is invented. Validation requires real conditional option-likelihood vectors, the pinned local runtime fingerprint, preserved input, sampled RSS and `calibrated: false`. An honest abstention is retained with `value: null`; conditional mass is not claimed to be calibrated probability of correctness. Semantic expected/actual candidates and mismatches are reported separately from execution/persistence success. The advice never authorizes, approves or formally verifies work.

The second independently issued GitHub owner session must reload the same source, human/assistant messages, model profiles and exact evaluation receipt. Anonymous artifact/evaluation reads must return application-level 401s. Both verification sessions are logged out. No model or queue job is automatically cancelled or replaced on failure. The private report retains synthetic resource IDs for diagnosis. Publish only reviewed screenshots and redacted aggregate evidence; internal deployment/database/job identifiers stay in private receipts. Resume with `STUDIO_HOSTED_LOCAL_AI_RESUME_FILE` and a fresh report destination; chat/review idempotency keys are persisted before admission so an uncertain response cannot create another inference run.

Read-only screenshots use `packages/studio/verification/hosted-local-ai-ui-live.mjs` with `STUDIO_HOSTED_LOCAL_AI_RECEIPT` pointing to a passed actual HTTP receipt and a fresh `STUDIO_HOSTED_LOCAL_AI_UI_EVIDENCE_DIR`. They use the same approved target/opt-ins and expected account, with a new private GitHub session export containing exactly one valid browser session. The screenshot protocol consumes and logs out that session; it does not perform an external OAuth exchange. `STUDIO_BROWSER_EXECUTABLE` may select the operator's installed Chromium. Keep TLS verification enabled; the managed public CA requires the environment's narrow NSS certificate-database access grant. Do not transfer a personal browser profile or GitHub provider token; only the explicitly selected exact-origin Studio cookie export is consumed.

The screenshot protocol checks current catalogs/source again, blocks foreign requests and page mutations, and captures actual saved chat, generative/decision pickers and retained predicate/choice results. Each claimed target must fit inside its viewport. Every final image must be opened and visually reviewed before publishing. Captions must pin the reviewed source commit and the bounded synthetic workload, distinguish native T3 from the explicit CPU alternative, and report actual uncertainty/semantic mismatches. Routed WebSocket observations do not establish native HTTP 101 or general collaboration acceptance. No inference, source change, model purchase or Gateway call is performed by the screenshot protocol.
