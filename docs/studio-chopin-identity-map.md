# Chopin identity and ownership comparison

The public Chopin README distinguishes instance admission, repository permissions, Planner ownership and model credentials. Studio keeps these boundaries separate too, while supporting non-repository media projects and automatic GitHub-only sign-in.

| Boundary | Studio behavior | Evidence and limits |
| --- | --- | --- |
| Instance admission | A genuine GitHub OAuth identity automatically receives a passwordless internal user. No local signup, email claim, owner-email configuration or login invitation is required. Exact identity bindings preserve continuity; email cannot claim another account. | Controlled OAuth/browser and PostgreSQL tests retain their fixture boundaries. Production requires a separate real-account callback receipt. Password and organization OIDC login are disabled. |
| Project access | Local project membership and role are required independently of GitHub access. Repository-backed projects additionally require the selected user's actual pull or push entitlement. | Real local GitHub HTTP OAuth/API fixtures; a project member without a repository connection receives 403 for a repository-backed artifact. Public repositories do not make projects public. |
| Credential persistence | PKCE/state/cookie-bound OAuth, one-use SQL challenges, AES-GCM token vault with a stable deployment key, rotating refresh and revocation. | Shared generation/version/permission fences and cross-instance refresh/revoke tests. Provider permission changes are bounded by the configured lease TTL unless a signed invalidation arrives first. |
| Repository tools | Bounded typed reads accept a selected authenticated user's token through the identity adapter. Tree reads pin a commit and cap entries; file/PR/issue/commit tools do not write a repository. | Identity adapter tests assert the actual user token on HTTP requests. Agent and remote Planner injection must use this adapter when per-user identity is enabled; operator token fallback is not a member entitlement. |
| Planner ownership | Shared SQL ownership and usage policy bind work to an admitted writer and fence publication after ownership/source changes. | Separate durable agent/conversation/title tests. Studio's owner lease is durable and may outlive an application restart until expiry; this differs from Chopin's documented process-released ownership. |
| Model credentials | The selected harness/provider/model is explicit. T3 is the default; Vercel/fx is an explicitly saved alternative using operator-configured provider credentials. | Local HTTP provider protocol fixtures prove transport and state transitions. They do not prove a real provider subscription, Copilot entitlement or production tenant setup. |
| MCP identity | Studio authenticates its own scoped bearer principal, then enforces the linked user's project/repository permissions. | This differs from public Chopin's direct GitHub bearer-token MCP login. A token or agent name supplied in an editable report cannot choose human approval or reviewer identity. |

Repository OAuth configuration and a successful local protocol fixture do not establish a live GitHub App installation or organization approval. Deployment acceptance must use the deployment's actual provider registration, stable encryption key, database and credentials. The implementation graph separately records repository/branch/commit provenance and independent verification; a declared checkout is not a remote checkout inspection.
