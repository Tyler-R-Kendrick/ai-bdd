# Studio on Vercel

Studio's Vercel composition uses a static Vite frontend, native queue functions, and a stateless container service. PostgreSQL owns application state, collaboration events/presence, frozen job inputs, leases, publication receipts, upload reservations, and maintenance intents. Private Blob owns asset bytes, evidence, rendered media, and bounded workspace snapshots. `/tmp` is disposable staging. The application's object, workspace, dispatcher, scheduler, and SQL interfaces allow replacement providers.

This runbook describes the implemented deployment path. The [live resource receipt](studio-evidence/vercel-release/live-resources.md) records actual Neon production/preview branches, separate private Blob stores, a private VCR manifest, and successful direct Blob/Sandbox SDK probes. Hosted application health, queue delivery/recovery, successful inference, and coordinated restore acceptance require separate results in the [readiness record](studio-readiness.md).

## Services and trust boundaries

The repository-root `vercel.json` defines the static `frontend`, container `backend`, and four native Node services: `jobs`, `maintenance`, `bootstrap`, and `identity`. The backend entrypoint is the repository-root `Dockerfile.studio`, so the container builder’s Dockerfile-directory context contains `pnpm-lock.yaml`, `pnpm-workspace.yaml` and every workspace package. Keep the canonical Dockerfile at that root; moving it under `packages/studio` narrows the platform context and makes workspace `COPY` instructions fail. Root `.dockerignore` constrains the Docker/Buildah image context and excludes local dependencies, generated build metadata, credentials and worktrees. The separate root `.vercelignore` protects the CLI source upload before that build; one ignore policy does not replace the other. The [actual CLI source-selection receipt](studio-evidence/vercel-release/source-inputs.md) records exclusion canaries and retained workspace/CAD build inputs.

The frontend builds `packages/studio/dist/client`, including the separately loaded CAD WASM. Native queue consumers are separate Node services with the existing `api/studio-jobs.ts` and `api/studio-maintenance.ts` entrypoints. Each owns its `queue/v2beta` trigger, duration, retry, and concurrency settings. They have no public service rewrite. The bootstrap service owns `api/studio-maintenance-bootstrap.ts`; only its exact authenticated bootstrap route is public. The jobs, maintenance, and bootstrap services each receive a generated `STUDIO_BACKEND_URL` binding and send bounded signed requests to the backend. The private identity service has no public rewrite and no reverse backend binding; only the backend receives its generated `STUDIO_IDENTITY_URL` binding. The backend image supplies Chromium and FFmpeg for supported server work; cloud media execution uses its separately pinned private Sandbox image.

Services resolves one builder per service. A `functions` map on the Vite static service did not create native API builders: the actual `52a6c61` preview returned HTTP 200 for backend health but platform `NOT_FOUND` for bootstrap, and its SQL schedule remained empty. The corrected configuration declares explicit `runtime: "node"` services. Each uses `node --check <entrypoint>` as its build-command syntax preflight; the official Node builder still transpiles, traces, and packages the entrypoint afterward. Without that explicit command, the actual `fb004a7` deployment ran the Studio package build and failed because workspace SDK declarations were not prebuilt in the deployment source. This preflight avoids that unrelated package build; full repository type checks remain a separate CI gate. These observations establish the failure and source correction, not successful hosted queue delivery.

The native identity service acquires a platform OIDC token inside its authenticated request handler. A deployment-bound nonce and HMAC protect both the lease request and response. The backend verifies RS256 signatures against the fixed global Vercel JWKS and checks the exact configured issuer, audience, subject, owner, project, and environment. The application grant lasts at most five minutes and must fit inside the upstream token lifetime with a safety margin; it does not shorten the JWT’s own cryptographic lifetime. Provider SDK callbacks receive the verified token only through an isolated execution context. Tokens are not written to environment variables, SQL, files, logs, browser responses, or a long-lived token cache.

Set the nonsecret trust configuration `STUDIO_IDENTITY_OWNER_ID`, `STUDIO_IDENTITY_OWNER_SLUG`, `STUDIO_IDENTITY_PROJECT_NAME`, `STUDIO_IDENTITY_ISSUER`, and `STUDIO_IDENTITY_AUDIENCE` in each cloud environment. The project ID, deployment ID, and environment come from trusted `VERCEL_PROJECT_ID`, `VERCEL_DEPLOYMENT_ID`, and `VERCEL_ENV` metadata. Do not derive trust settings from an incoming JWT or manually replace generated service-binding URLs. The identity service and backend use the deployment’s existing `STUDIO_JOB_SECRET` for their private HMAC exchange.

The actual platform launch in this release used Docker's `CMD`, `node dist/server/main.js`, and did not honor `services.backend.command` as a replacement. The default entrypoint selects `STUDIO_HOSTING_PROVIDER` (or the platform's Vercel metadata) before evaluating local settings, dispatches to the cloud composition when selected, and fails closed for an unknown provider. Keep that dispatch in the default image entrypoint; an explicit cloud command alone does not protect the observed platform launch path.

The service binding grants reachability, not authorization. Internal requests use a 60-second HMAC bound to method, exact path, timestamp, and exact body. Public rewrites expose `/api/*` domain routes and the authenticated maintenance bootstrap, never `/internal/*`. Queue consumers are private platform triggers. A response or queue send receipt confirms dispatch; a fenced SQL publication receipt determines completed work. Queue delivery is at least once, and external provider operations can repeat after an uncertain response.

Static responses carry the application CSP and security headers directly in the frontend service configuration. The app does not allow general `unsafe-eval`. Only a generated `/assets/kernel.worker-<hash>.js` response permits the OCCT embind string compiler. Browser uploads may connect to the actual SDK endpoint `https://vercel.com/api/blob/`; private media stays behind authorized same-origin file routes. Do not broaden these sources to arbitrary origins.

## Provision and configure

1. Use the explicitly authorized Vercel team and approved GitHub repository. The release-time repository visibility observation is public; do not assume an older private-repository description still applies or change visibility as part of deployment. Confirm that Services/container images and Queues are enabled for that project and plan. The configuration uses Node 24, one matching deployment/queue region and a 300-second request budget. Container limits are 300 seconds on Hobby and up to 800 seconds on eligible plans; extended native-runtime limits do not apply to this container. Keep actual team/project identifiers and operational deployment references in private operator configuration.
2. Create an external PostgreSQL database, such as Neon, near the selected deployment region. Give preview deployments their own database branch and credentials. `DATABASE_URL` must use verified TLS for a remote endpoint. Prefer the provider's pooled connection URL; the adapter uses a bounded pool and transaction-scoped advisory locks. Never put SQLite on a Vercel filesystem or attempt to synchronize SQLite snapshots between instances. Keep actual database/branch/endpoint identifiers in private bindings.
3. Connect a **private** Vercel Blob store. Provide its `BLOB_READ_WRITE_TOKEN` through Vercel secret environment bindings. Standard browser upload grants require this signing credential; server-side Blob supports provider OIDC, but that does not replace the current bounded client-token signer. Use different stores or isolated credentials for production and previews.
4. Generate stable, independent secrets for `STUDIO_JOB_SECRET` and `CRON_SECRET`, each at least 32 characters. Keep the job secret identical across the native consumers and their backend service in a deployment. Retain it while old deployment-pinned queue deliveries drain. Set `STUDIO_REPOSITORY_TOKEN_KEY` to an independent 32-byte base64url key when repository OAuth is enabled; changing that encryption key without a migration makes saved repository credentials unreadable.
5. Set `STUDIO_HOSTING_PROVIDER=vercel`, `NODE_ENV=production`, `STUDIO_QUEUE_REGION` to the selected queue region, and the exact production `STUDIO_ORIGIN=https://ai-bdd-studio.vercel.app`. The runtime derives preview origins from trusted `VERCEL_URL` metadata; it does not use a request Host or forwarded host. Leave `STUDIO_PORT` unset so the container listens on platform `PORT`, defaulting to 80. Do not copy the local Docker port override into Vercel.
6. Configure the authorized owner `STUDIO_ADMIN_EMAIL` and prefer the owned managed GitHub connector through `STUDIO_GITHUB_SIGNIN_CONNECTOR`. Attach it to the intended Vercel project and environments; Vercel Connect manages the upstream GitHub application, so Studio needs no manual GitHub client secret for this adapter. Studio serves `/api/auth/github/callback`. The explicit direct OAuth adapter outside Connect instead uses separate `STUDIO_GITHUB_SIGNIN_CLIENT_ID` and `STUDIO_GITHUB_SIGNIN_CLIENT_SECRET` bindings and an exact registered Studio callback. Password, setup, demo, and generic organization OIDC login are disabled. Restrict admission to existing invited accounts and the verified first-owner email. Project-authenticated connector metadata and attachment checks do not establish a successful real browser callback; run that acceptance separately. Repository authorization remains a separate consent flow: when enabled, configure `/api/identity/github/callback`, signed webhook `/api/auth/repository/github/webhook`, and the complete trio `STUDIO_GITHUB_CLIENT_ID`, `STUDIO_GITHUB_CLIENT_SECRET`, `STUDIO_REPOSITORY_TOKEN_KEY`. When disabled, leave all three unset. Partial configuration deliberately refuses startup. Direct OAuth preview callbacks need deliberate provider registration; a production callback is not automatically valid for a preview hostname.
7. The default model path uses pinned downloaded **Qwen2.5 0.5B Q4_K_M** weights. The controlled image build verifies the model and genuine T3/OpenCode tools; local inference performs no downloads and needs no AI Gateway account or purchase. Keep `STUDIO_T3_STATE_KEY` as a stable independent server-only encryption key in each environment so encrypted native checkpoints can be restored. T3 Code is the default authoring harness with that local CPU provider. The explicit Local CPU alternative runs through the Vercel AI SDK without changing the default harness. The independent decision picker defaults to `llama-cpp-cpu / qwen2.5-0.5b-instruct-q4-k-m`, freezes its own threshold/model provenance, and returns uncalibrated finite-label likelihoods with abstention. Optional Gateway authoring, structured generation and native evaluation need explicit registration and must pass the [free-only policy](studio-free-models.md) on every attempt: fresh complete zero-price metadata, a verified free-provider allowlist and no paid fallback. Two bounded live probes returned HTTP402 before completing inference; no purchase or successful Gateway acceptance is claimed. An unconfigured or unavailable alternative never replaces the local defaults. See [managed native T3](studio-t3-local-runtime.md), [local decisions](studio-local-decisions.md), and the source-pinned [readiness record](studio-readiness.md). Any external native T3 registration retains supervised permission/provenance checks and the production free-only model policy; registration alone does not enable an unverifiable paid provider.

8. Deploy from the repository root so all six services, bindings, private queue triggers, and the daily Cron job are included. Retain `.vercelignore` in the CLI source selection and the Docker ignore policies in the selected builder inputs. Preserve `VERCEL_DEPLOYMENT_ID`, `VERCEL_URL`, and OIDC metadata supplied by the platform. Provider emulator overrides and demo bootstrap are rejected in the Vercel runtime.

See [`.env.example`](../packages/studio/.env.example) for variable names. Never commit populated environment files, shell history containing credentials, or service tokens to PR comments. Bindings and OIDC metadata are generated by Vercel rather than typed by an application user.

## Activate recovery and verify the deployment

Cloud startup uses a dispatch limit of zero: it can restore durable intent without attempting provider publication before the service is listening. A queue outage leaves pending work visible as degraded execution readiness while manual authoring remains available. Authenticated maintenance performs the bounded provider dispatch and recovery.

After a successful deployment, invoke `GET /api/studio-maintenance-bootstrap` with `Authorization: Bearer <CRON_SECRET>` using a secret-aware client. Do this for production promotion and for each preview that will execute durable work. The daily production Cron supplies the same authorization and repairs an interrupted schedule. Bootstrap uses trusted deployment metadata to activate one SQL generation. Cold starts of an old deployment do not rotate that generation.

Each accepted tick persists its unique successor before domain maintenance, then reconciles queued/expired job leases and expired upload reservations. The successor is delayed to the next minute. SQL generation checks, leases, and unique bucket identities prevent duplicate deliveries from multiplying schedules. Old deployment ticks acknowledge without rearming. A failed/uncertain publication retries with its original intent ID; a new recovery intent receives a new ID. The chain still depends on the provider accepting and delivering messages; the daily Cron is its independent bootstrap, not a continuous-availability guarantee.

Use two separate signed-in browsers and separate backend instances for the release rehearsal:

- Check `/api/health` and `/api/hosting/readiness`. Readiness verifies SQL connectivity and distinguishes **configured** object/queue adapters from live end-to-end verification; it does not manufacture successful Blob or queue checks.
- Create a project, edit a document concurrently, reconnect a client, and confirm persisted content, authorized discussion, and presence expiration. Revoke a collaborator and verify subsequent writes, asset reads, and job publication fail.
- Upload an allowed image and a video larger than 4.5 MB. The browser must receive an exact immutable, size-limited private grant; completing it must sniff the actual media and recheck membership. Download through `/api/files/:id` and verify unauthorized users cannot read the bytes. A failed provider request must not silently downgrade to local storage.
- Select a registered T3 provider/model (or explicitly select the configured Vercel/fx alternative), send an artifact request, and inspect its actual persisted result. Run the configured acceptance task and a video render. Inspect their actual visual evidence/output, persisted job state, source version, and permissions. Terminate the worker during a leased step, allow recovery, and verify stale attempts cannot overwrite the canonical result. External side effects may need provider idempotency or reconciliation; do not call them exactly once.
- Open exact CAD, perform a sketch/extrusion and STEP export, and confirm the app CSP stays unchanged while the trusted CAD worker starts. Exercise code previews and rendering with real browser console/network checks.
- Rotate to a new deployment, bootstrap maintenance, and observe old ticks retiring. Confirm queued work is either completed under its immutable snapshot or transparently failed/cancelled according to its bounded retry policy.

Keep request/lease deadlines below the configured plan limits. If changing `STUDIO_REQUEST_SECONDS`, update native function `maxDuration`, queue visibility settings, and the container service budget together. Maximum deliveries are bounded at ten and retention at one day. SQL outbox/recovery is authoritative after a provider receipt expires. Configure provider retry-depth/runtime-error alerts and an operational response to a failed daily bootstrap.

## Backup, restore, rollback, and replacement

Back up PostgreSQL using the provider's supported point-in-time/branch tooling and retain matching private objects. A database backup without its immutable object keys is incomplete. Pause new work for a coordinated restore point, retain SQL job/step/publication receipts and upload reservations, and keep old objects until the restore rehearsal proves they are unnecessary. Secret encryption keys and provider bindings need a separate protected recovery process.

Restore into a separate database branch and private store or a read-only copy of the required immutable keys. Start a separate preview deployment with those bindings, activate its own schedule, sign in, inspect representative artifacts/chats/ADRs, download assets/evidence, and resume or explicitly cancel restored jobs. Verify recorded workspace hashes during restoration. Promote only after that rehearsal; retain the prior production bindings and deployment for rollback. A code rollback against a changed SQL schema also requires checking migration compatibility.

Replacing Vercel means supplying implementations of `ObjectStore`, `WorkspaceStore`, `JobDispatcher`, `SchedulerDispatcher`, and `SqlDatabase` and a composition root. Domain services consume those ports. A replacement transport must preserve job-ID-only messages, stable per-intent dispatch keys, delivery deadlines, at-least-once recovery, and SQL fencing. Disk objects and the local dispatcher remain supported development/single-host alternatives; their availability model is separate from managed PostgreSQL/Blob/Queues.

The container receives SIGTERM during shutdown. The host marks readiness as draining, closes workers and sessions, and uses a bounded 25-second exit budget within the platform grace period. `/tmp` contents are discarded; restore durable workspaces from verified private object references after restart. Configure trusted proxy CIDRs only when their actual ingress addresses are known; never derive identity or canonical origin from forwarded headers.
