# Artifact archive lifecycle

Artifacts can be archived, read in the archive, restored, or permanently removed when no retained dependency requires them. The project's main design artifact remains active. Owners manage archives; editors and viewers can browse and read them.

The archive browser keeps the normal artifact canvas, chat, decisions, versions, and evidence available in read mode. Restore uses both the source version and archive revision captured during review. It does not accept decisions, approve a graph, or create a new build.

An already-running implementation or existing-PR rebuild can continue reporting under its original scoped credentials after archival, including independent verification. Archiving does not stop a connected process or discard its progress. New claims and source writes are refused. Other active AI, media, investigation, remote background activity, and unexpired upload capabilities must settle before the corresponding destructive action is available. Restoring does not clear a running graph's source-edit lock.

Permanent removal requires an owner session, the exact archived source version and archive revision, and the exact artifact title. The UI additionally asks for an explicit acknowledgement. A stale confirmation is refused and must be reviewed again. The API refuses bearer-only deletion, including a bearer supplied alongside a person session.

The server holds the project mutation lock, rechecks the current role and repository entitlement, and inspects dependencies in the same SQL transaction. Published investigations and their children, acceptance runs, implementation runs, delivered baselines, rebuild verification receipts, retained test workspaces, cross-artifact references, and immutable asset references prevent deletion. These artifacts can remain archived. Saved text and JSON fields in artifact-owned tables and indirect chat/job records participate in reference discovery. Unknown direct or indirect foreign-key dependencies default to a typed refusal rather than silent cascading. Known terminal Planner assignments, remote question/activity metadata, findings review metadata, durable receipts, and media staging can cascade with an eligible draft; queued or claimed Planner assignments block archive and deletion. Published investigation and build evidence still blocks deletion before that cascade is considered.

For an eligible draft, removal atomically cascades its own content, revisions, chats, ADRs, files, and known terminal sidecars. A minimal project-level deletion receipt remains after the artifact row is gone. Retrying the confirmed request returns that receipt. Records carrying retained proof are never treated as disposable sidecars.

Private object deletion happens after the SQL deletion commits. It has a bounded batch, deadline, SQL lease, retry backoff, and a permanent hash tombstone for each removed immutable object key. The shared file-registration guard checks that tombstone under a global SQL lock, preventing a concurrent registration from resurrecting a key while an external delete is in flight. Physically shared registered objects are retained for their surviving owner. Cleanup can resume in another application instance; a provider failure does not turn the committed artifact deletion into a failed deletion. Maintenance must call `artifactLifecycle.cleanup()`.

Implementation: `server/artifact-lifecycle.ts`, `shared/artifact-lifecycle.ts`, and `client/components/ArchivePanel.tsx`. The application supplies its existing authenticated ObjectStore, graph lock, collaboration notification, and artifact-wide remote-activity check. No cloud SDK is embedded in the lifecycle service.
