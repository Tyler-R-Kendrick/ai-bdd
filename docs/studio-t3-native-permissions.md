# Native T3 permission admission

T3 remains the default authoring harness. It is unavailable until the operator registers a native MCP endpoint, a client approved in T3 for **Supervised** (`approval-required`) access, an absolute native project workspace and concrete native provider/model IDs. Studio does not substitute Vercel/fx when T3 is unavailable. Choosing Vercel/fx remains an explicit saved action.

The adapter uses the real T3 MCP API. It does not spawn `t3 thread start`: native T3 0.1.5 has no CLI start permission flag, starts with the project's effective defaults, and initially defaults to Full Access. The old CLI command/argument registration remains accepted as compatibility metadata; CLI-only generation reports unavailable. No dummy CLI command is needed for MCP registration.

An operator registers `STUDIO_T3_MCP_URL`, `STUDIO_T3_MCP_ACCESS_TOKEN`, `STUDIO_T3_PROJECT` and `STUDIO_T3_PROVIDERS_JSON`. The endpoint uses HTTPS in production. Keep the approved client token in the deployment's secret manager. The project must exactly match one native `workspaceRoot`; Studio makes no assumptions about a remote directory existing on its own filesystem. Provider IDs are native provider-instance IDs, and model IDs must be present in that instance's advertised catalog. Registration is not a permission attestation: each generation verifies the native endpoint again.

Before native work, Studio requires the public launch tool's explicit permission/idempotency fields, a native caller ceiling of `approval-required`, an advertised selected model supporting that mode, and a project list/read with the registered absolute workspace. The launch sends the exact project, provider/model, **explicit `runtimeMode: "approval-required"`**, and a stable native `clientRequestId`. This makes a project default change irrelevant to the launch mode and permits recovery after an uncertain HTTP reply. No CLI generation fallback exists.

Every native thread read and text chunk checks the exact thread, project, provider, model, runtime mode and run. A missing field or changed scope prevents acceptance of the result. Native permission/input requests remain pending for a person in T3; Studio never calls approval/answer tools. Cancelling a known running request or rejecting its readback provenance attempts to interrupt that exact native thread/run through a separate bounded MCP connection; this is a best-effort request, not a claim that the native provider stopped. Requests have a 180-second deadline, the native 120,000-character prompt limit, bounded timeline/chunk reads and HTTP response budgets. The adapter passes no process environment or local model credential to a subprocess.

Supervised is a native permission mode, not a claim that every provider implements identical sandboxing. The pinned native Codex adapter maps it to `approvalPolicy: "untrusted"`, human review and `sandboxPolicy: {type: "readOnly"}`. Other drivers and explicit native operator policy overrides are part of the trusted T3/provider configuration. Studio does not approve a native permission request, configure Full Access, or claim that prompt instructions enforce a sandbox.

## Validation boundary

`t3-native-permissions.test.ts` uses a local HTTP MCP protocol fixture matching the public tool names, schemas and structured results. It covers a Full Access project default, rejected caller ceilings/schema/provider/project configuration, exact readback fences, an uncertain launch reply with one idempotent native execution, a changed recovered thread, unapproved requests, chunk provenance and prompt bounds. A real child-process marker proves the unsafe CLI is never started. `t3-harness.test.ts` exercises the actual installed AI SDK's tool orchestration, structured response validation, durable frozen profile, exact-run cancellation and visible offline selection. These checks establish adapter/protocol behavior. They do not establish a successful call to an external T3 provider or a paid model.
