# GitHub sign-in

Studio accepts GitHub browser sign-in. Email/password setup, login, demo login and password changes return HTTP 403 even when a valid historical password exists. Organization OIDC login routes are unavailable. An unconfigured GitHub provider fails closed; it does not reveal a fallback form.

The preferred Vercel adapter uses `STUDIO_GITHUB_SIGNIN_CONNECTOR`, set to the UID returned by the owned managed GitHub connector setup. Attach that connector to the intended Vercel project and environments. Studio serves `${STUDIO_ORIGIN}/api/auth/github/callback`; Vercel Connect manages the upstream GitHub application and its provider callback. No GitHub client secret is required in Studio for this adapter. `STUDIO_ORIGIN` must be the canonical HTTPS origin in production.

The explicit direct OAuth adapter remains available outside Connect: bind `STUDIO_GITHUB_SIGNIN_CLIENT_ID` and `STUDIO_GITHUB_SIGNIN_CLIENT_SECRET`, and register the exact Studio callback with that owned GitHub application. A configured Connect UID takes precedence over direct OAuth settings. Keep secrets in deployment bindings and do not send secret values through chat.

Live managed login requires completed connector setup and the correct project/environment links. A controlled issuer fixture cannot supply those prerequisites or establish a successful live GitHub login. A different deployment origin must belong to the authorized environment; caller-supplied redirect destinations are never accepted.

For the current release, the approved managed GitHub connector is attached to the Studio project in production, preview and development, its nonsecret selector is bound, and a real project-authenticated connector metadata check passed. No manual GitHub OAuth secret registration is needed for that adapter. The successful managed browser callback and deployment of the new source remain separate acceptance gates; those setup checks do not establish either one.

`GET /api/auth/github` starts the authorization code flow. Studio requests GitHub `user:email` access, uses S256 PKCE and stores a five-minute, one-use SQL challenge bound to a separate HttpOnly browser cookie. The callback checks the challenge before exchanging a code. GitHub access tokens are used only for the fixed profile and verified-email API requests; sign-in does not persist them. Transport follows no redirects, applies time and response-size bounds, and returns no provider messages or credential data. Failed callbacks return to the fixed `/?signin=failed` page.

The Connect adapter uses the pinned official `@vercel/connect/authjs` OAuth configuration and its fresh project OIDC authentication. The backend's existing validated identity sidecar scopes each SDK operation; no project JWT is supplied by a browser or copied into a worker. The authorization code exchange uses PKCE, the browser-bound one-use SQL state and fixed Connect HTTPS endpoints. A token-subject exchange using only that server-obtained OAuth session requests GitHub `user:email` access, then the actual GitHub API resolves the numeric account ID and verified emails for the existing admission rules. No app grant, caller-selected user ID, opaque Connect subject or optional Connect profile email authorizes login.

Connect requests `user:email` and the SDK-added `offline_access` scope. The flow does not request an OIDC nonce or require an ID token or Connect userinfo claims. If an optional ID token is returned, the pinned OAuth client still validates issuer, audience, timestamps, nonce absence and its RS256 signature; its claims do not determine the Studio account. Returned refresh tokens are discarded, and temporary provider-token cache entries are evicted after the sign-in check. Studio retains only its hashed session and GitHub identity binding. SDK operations have a deadline; OAuth discovery, token and optional JWKS transport also enforce fixed HTTPS endpoints, redirect refusal and bounded response bodies. Failure diagnostics contain only finite stages, timing, allowlisted error classifications and token-shape booleans; they exclude provider text and credential or identity values.

Set `STUDIO_ADMIN_EMAIL` to the first owner's verified GitHub email before starting a new workspace. The first successful GitHub sign-in can create that owner only while no users exist. Other people must already have an invited workspace account with a matching verified GitHub email. A matching email may be non-primary or private on GitHub. Public signup and ambiguous matches to multiple workspace accounts are refused.

The first admitted sign-in binds GitHub's stable numeric account ID to the existing Studio user ID. Project roles, artifacts and native checkpoint ownership stay attached to that Studio ID. Later GitHub email changes do not move the account, and another GitHub ID cannot claim an already-bound account through a matching email.

New browser sessions receive durable GitHub provenance. Historical password-created browser cookies remain unauthorized after the cutover, including pending repository-connection callbacks. Session tokens are stored as hashes, and logout/revocation removes their provenance through the session foreign key. Existing explicitly scoped API bearer credentials retain their separate `kind='api'` authorization policy; they cannot be presented as browser cookies.

Repository authorization remains a separate consent and permission boundary. GitHub sign-in neither grants repository access nor supplies an operator token to repository tools. `STUDIO_GITHUB_CLIENT_ID`, `STUDIO_GITHUB_CLIENT_SECRET` and the repository credential vault configure that separate adapter.

The focused tests use an owned injected provider or loopback HTTP issuer to exercise real SQL challenges, PKCE, callback admission and session publication. The PostgreSQL cases exercise competing owner bindings and callback replay across application instances. These checks do not establish a live GitHub application's callback configuration or replace deployment acceptance with that application.
