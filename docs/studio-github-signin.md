# GitHub sign-in

Studio accepts GitHub browser sign-in. Email/password setup, login, demo login and password changes return HTTP 403 even when a valid historical password exists. Organization OIDC login routes are unavailable. An unconfigured GitHub provider fails closed; it does not reveal a fallback form.

The preferred Vercel adapter uses `STUDIO_GITHUB_SIGNIN_CONNECTOR`, set to the UID returned by the owned managed GitHub connector setup. Attach that connector to the intended Vercel project and environments. Studio serves `${STUDIO_ORIGIN}/api/auth/github/callback`; Vercel Connect manages the upstream GitHub application and its provider callback. No GitHub client secret is required in Studio for this adapter. `STUDIO_ORIGIN` must be the canonical HTTPS origin in production.

The explicit direct OAuth adapter remains available outside Connect: bind `STUDIO_GITHUB_SIGNIN_CLIENT_ID` and `STUDIO_GITHUB_SIGNIN_CLIENT_SECRET`, and register the exact Studio callback with that owned GitHub application. A configured Connect UID takes precedence over direct OAuth settings. Keep secrets in deployment bindings and do not send secret values through chat.

Live managed login requires completed connector setup and the correct project/environment links. A controlled issuer fixture cannot supply those prerequisites or establish a successful live GitHub login. A different deployment origin must belong to the authorized environment; caller-supplied redirect destinations are never accepted.

For the current release, the approved managed GitHub connector is attached to the Studio project in production, preview and development, its nonsecret selector is bound, and a real project-authenticated connector metadata check passed. No manual GitHub OAuth secret registration is needed for that adapter. The successful managed browser callback and deployment of the new source remain separate acceptance gates; those setup checks do not establish either one.

`GET /api/auth/github` starts the authorization code flow. Studio uses S256 PKCE and stores a five-minute, one-use SQL challenge bound to a separate HttpOnly browser cookie. The callback checks the challenge before exchanging a code. Transport follows no redirects, applies time and response-size bounds, and returns no provider messages or credential data. Failed callbacks return to the fixed `/?signin=failed` page.

The Connect adapter uses the pinned official `@vercel/connect/authjs` OAuth sign-in configuration and its fresh project OIDC authentication. The backend's existing validated identity sidecar scopes each SDK operation; no project JWT is supplied by a browser or copied into a worker. The server exchanges the authorization code, then uses its OAuth access token only at the fixed Connect userinfo endpoint. The owned connector must identify the GitHub service. Studio requires a bounded opaque userinfo subject; email and email verification claims are optional and do not determine access. The exact Connect issuer, canonical connector ID and opaque subject form the durable identity key. Subject format does not confer authorization. Sign-in requests no provider API credential or app grant, and never exchanges this OAuth access token as a Passport subject token.

Connect requests the official `openid profile email` scopes, GitHub `user:email`, and the SDK-added `offline_access` scope. The OAuth/PKCE flow does not request an OIDC nonce or require an ID token. If an optional ID token is returned, the pinned OAuth client still validates issuer, audience, timestamps, nonce absence and its RS256 signature, and requires its subject to match userinfo. Returned refresh tokens and OAuth access tokens are discarded. Studio retains only its hashed session and qualified identity binding. SDK operations have a deadline; OAuth discovery, token, userinfo and optional JWKS transport enforce fixed HTTPS endpoints, redirect refusal and bounded response bodies. Failure diagnostics contain only finite stages, timing, allowlisted error classifications and token/profile-shape booleans; they exclude provider text and credential or identity values.

A successful GitHub sign-in automatically creates the internal passwordless user record on first use. No local signup, pre-created account, invitation, email claim, or `STUDIO_ADMIN_EMAIL` is required. GitHub manages the credentials; Studio stores the user ID needed to associate projects, artifacts and permissions with that identity.

The exact managed issuer/connector/subject or direct numeric GitHub ID identifies the account. Existing bindings retain their Studio user ID. First sign-in inserts a fresh record and identity binding in one transaction under the admission lock, so simultaneous callbacks for the same principal converge on one account. New records use a random identifier in the reserved `identity.invalid` namespace to satisfy the historical database column; that value is an internal identifier, not a contact or verified email. Profile email changes, missing email, private email and another identity using the same email cannot transfer account ownership. Direct OAuth needs only the authenticated GitHub profile; it does not depend on the private-email endpoint.

Project membership remains separate from login. A new identity can create its own projects and starts with no access to another user's projects. To share an existing project, its owner adds the teammate's Member ID after the teammate signs in with GitHub. The account sidebar exposes that ID for copying. Login does not need a project invitation. Historical email-created placeholder records are not silently reassigned to a GitHub identity; email is never proof of ownership.

New browser sessions receive durable GitHub provenance. Historical password-created browser cookies remain unauthorized after the cutover, including pending repository-connection callbacks. Session tokens are stored as hashes, and logout/revocation removes their provenance through the session foreign key. Existing explicitly scoped API bearer credentials retain their separate `kind='api'` authorization policy; they cannot be presented as browser cookies.

Repository authorization remains a separate consent and permission boundary. GitHub sign-in neither grants repository access nor supplies an operator token to repository tools. `STUDIO_GITHUB_CLIENT_ID`, `STUDIO_GITHUB_CLIENT_SECRET` and the repository credential vault configure that separate adapter.

The focused tests use an owned injected provider or loopback HTTP issuer to exercise real SQL challenges, PKCE, automatic identity provisioning and session publication. The PostgreSQL cases exercise competing identity provisioning and callback replay across application instances. These checks do not establish a live GitHub application's callback configuration or replace deployment acceptance with that application.
