# GitHub sign-in and repository identity evidence

Genuine GitHub sign-in automatically provisions a passwordless internal account without email claims, a configured owner email, a pre-existing local account or an invitation. Password and organization OIDC login are disabled. GitHub repository identity is a separate, optional per-user OAuth connection: when configured, project membership and the selected user's actual GitHub pull/push permissions are both required for repository-backed projects. Without it, repository tools and PR refresh use only anonymous public requests. Legacy operator tokens and repository allowlists never authorize user-scoped reads.

`tests/repository-authority.test.ts` covers fresh GitHub accounts against owned private/public HTTP responses, including actual MCP/API/AI-SDK file-tool execution, private PR state/head refusal, anonymous public success, per-user connection capability, independent personal OAuth and disconnect. Its PostgreSQL matrix requires the local fixture in CI. Dummy operator credentials must never reach these requests; inaccessible private content must not enter model prompts or persisted chat. Selected-user transport, permissions, cancellation, revocation and lease tests remain in `repository-tools.test.ts`, `repository-identity.test.ts`, `runtime-repository-leases.test.ts` and `pull-request-head.test.ts`. Controlled fixtures do not establish a successful production GitHub callback or live private repository acceptance.

The current `tests/identity.spec.ts` browser workflows use owned GitHub code/PKCE providers for automatic signup, optional email claims, durable-state replay/expiry refusal, token failure, disabled legacy routes and the separate per-user repository connection. The older evidence below records the 2026-10-30 organization-admission workflow before the GitHub-only cutover; its images and issuer/password observations are historical and do not describe current login behavior.

## Historical organization-admission protocol evidence

`tests/identity.spec.ts` starts the complete application, an official oidc-provider 9.13.3 HTTP issuer, and an HTTP GitHub OAuth/API fixture. Six Chromium cases passed on 2026-10-30: admitted verified login through PKCE/signed ID token/UserInfo and callback replay rejection; GitHub connection/project creation/selected-user bounded read/member-without-GitHub denial/password login/disconnect; unadmitted denial; unverified denial; expired durable state before token exchange; token endpoint failure without a session. The fixture's accounts and provider credentials are synthetic. This is actual local protocol execution, not a live organization tenant or github.com credential acceptance claim.

The application browser flow caught a real capability-cache integration failure: a successful push preflight did not persist the provider-confirmed pull permission, so an internal project read failed. The service now atomically replaces both leases with exactly the capabilities in the actual provider response, preserving generation/version/permission-revision fences. Twelve identity unit/integration checks include a regression that pull-only responses remove stale push leases and neither capability is inferred from the other.

The seven dedicated issuer checks additionally cover independent HttpOnly cookie binding, state expiry, metadata issuer mismatch, lazy discovery recovery, and password availability during issuer outage. Durable challenge consumption uses DELETE RETURNING. Credentials use AES-GCM with deployment-configured stable keys; refreshing, disconnecting and signed-webhook invalidation operate through shared database state and transaction locks.
