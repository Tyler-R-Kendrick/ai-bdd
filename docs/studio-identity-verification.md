# Repository identity and organization sign-in evidence

The application supports optional organization OIDC alongside admitted password accounts. GitHub repository identity is a separate, optional per-user OAuth connection. Project membership and the selected user's actual GitHub pull/push permissions are both required for repository-backed projects; operator tokens and repository allowlists cannot grant a member entitlement.

`tests/identity.spec.ts` starts the complete application, an official oidc-provider 9.13.3 HTTP issuer, and an HTTP GitHub OAuth/API fixture. Six Chromium cases passed on 2026-10-30: admitted verified login through PKCE/signed ID token/UserInfo and callback replay rejection; GitHub connection/project creation/selected-user bounded read/member-without-GitHub denial/password login/disconnect; unadmitted denial; unverified denial; expired durable state before token exchange; token endpoint failure without a session. The fixture's accounts and provider credentials are synthetic. This is actual local protocol execution, not a live organization tenant or github.com credential acceptance claim.

The application browser flow caught a real capability-cache integration failure: a successful push preflight did not persist the provider-confirmed pull permission, so an internal project read failed. The service now atomically replaces both leases with exactly the capabilities in the actual provider response, preserving generation/version/permission-revision fences. Twelve identity unit/integration checks include a regression that pull-only responses remove stale push leases and neither capability is inferred from the other.

The seven dedicated issuer checks additionally cover independent HttpOnly cookie binding, state expiry, metadata issuer mismatch, lazy discovery recovery, and password availability during issuer outage. Durable challenge consumption uses DELETE RETURNING. Credentials use AES-GCM with deployment-configured stable keys; refreshing, disconnecting and signed-webhook invalidation operate through shared database state and transaction locks.
