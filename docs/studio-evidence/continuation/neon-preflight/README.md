# Neon provider preflight

This is a live provider check on the already-created task project `crimson-frog-10403185`, using two new isolated test branches. The source application revision is `4f4ddae638a82f850c1b620ea8f17b9750c5e5b9`. The production branch `br-shiny-fire-b8tn4wiv` received no schema/data mutations; a fresh read verified the test schema is absent there.

The workspace could not establish native PostgreSQL connections: direct and pooled endpoints both returned `ECONNREFUSED` before Store/App migration or HTTP startup. A direct attempt with additional network access had the same result. Connection strings were fetched privately and passed only through echo-disabled stdin/private process IPC; none were written into arguments, environment files, logs or this evidence. **This does not verify App HTTP, the shipping PostgreSQL transport against Neon, deployed integration, load capacity or an SLO.** The opt-in `verification/neon-preflight.ts` harness remains available for a network that can reach Neon PostgreSQL.

The connected Neon SQL transport did work against PostgreSQL 17.11. The actual default Node application initialized a new local PostgreSQL 17 schema. Its schema-only `pg_dump`, with owner/privilege commands absent and psql/comment metadata removed, produced [this captured DDL](captured-node-schema.sql). All 645 trusted statements applied transactionally through MCP to the isolated Neon source branch. A fresh provider read found 72 application tables and 298 constraints. This establishes schema portability for that composition, rather than proving the original migration execution path or every hosted adapter extension on Neon.

Synthetic records populated the real users/projects/memberships/artifacts/decisions/threads/messages/revisions tables, plus one separate test marker. A provider-created child copied that branch at its HEAD. After its source, accepted ADR, chat and marker were changed, a confirmed compute suspension followed by a fresh MCP read preserved the changed records. A deliberately failed SQL transaction left zero inserted rollback rows, and a foreign-key rejection check passed.

A provider `reset_from_parent` operation then reset **only the disposable restore child** to its untouched test parent's current HEAD. A fresh read restored the exact original source SHA256 (`ae2e44d98a2f97b3a6963ab3fff6baa1c596f40aa4d8fe7bc8e12ac65d799401`), source/ADR version 2, original accepted choice, one original message, two revisions and the original marker. The post-branchpoint message was absent. All 72 application tables and 299 validated constraints (including the extra marker's primary key) remained. The [machine-readable report](report.json) retains before/changed/resumed/restored rows.

This is a **branch reset to current parent HEAD**, not a PITR or snapshot-backup rehearsal. Neon rejected snapshot creation with HTTP 400, “not allowed to snapshot non-root branch.” The production root was not used as a workaround. Storage objects, external secrets/identity, hosted jobs, a live provider model and production restoration were not tested.

Three concurrent MCP requests completed in approximately 3.3, 6.5 and 10.1 seconds; these are connector round trips and do not establish concurrent database query execution or application latency. The resumed-compute read took 3.8 seconds and the post-reset read 4.0 seconds through MCP. No capacity/RTO/SLO claim follows from these bounded observations.

Both new computes were constrained to 0.25 CU, confirmed `idle` after suspension, and subsequently removed with their test branches. The account rejected a suspend-interval override with HTTP 412; the test explicitly suspended both computes. The local synthetic schema was deleted. Automatic approval review initially rejected remote branch removal because trusted user messages did not explicitly approve that exact deletion. Both computes were suspended while awaiting it. After the user explicitly approved the two named branches, `br-square-bread-b8co5ej3` was deleted first, then `br-hidden-dust-b8ilegv9`. A fresh provider listing confirms both test branches and their computes are gone and only production `br-shiny-fire-b8tn4wiv` remains. No indirect workaround was used.
