# Authoring availability during dispatch outages

Cloud startup uses `createApp(settings, { startupDispatchLimit: 0 })` to reconcile durable SQL intents and leases without contacting the queue provider. Authentication, manual document editing and integration-independent previews can therefore start during a dispatch outage. An unspecified option retains standalone/local startup behavior; a positive option bounds each startup dispatch pass. SQL/schema and domain authorization failures remain errors.

`OutboxDispatchPendingError` identifies a narrow recoverable boundary: the external dispatcher failed, and the coordinator successfully persisted the pending intent and retry backoff. Its fixed code/count contains no provider detail. Startup catches only this type. The provider call and its SQL receipt write have separate error boundaries: failing to save a successful dispatch receipt remains a storage error, with the intent/lease available for bounded replay. No receipt, completion or output is invented.

The human-message route also preserves this boundary. Text and conversation observations commit to SQL. Cloud title/agent follow-ups may admit durable jobs, but an async-scoped `deferDispatch()` prevents their nested flush calls from contacting a provider before the human acknowledgment. Its collector reports only fresh job IDs after their SQL transaction commits; existing idempotent jobs and rolled-back admissions are excluded. Other concurrent scopes retain normal dispatch. The local default still attempts publication and ignores only the typed, safely persisted dispatch failure after text has committed. SQL and domain authorization errors are not broadly suppressed.

After the HTTP response finishes, a small helper promptly publishes only those newly admitted IDs through `flushOutbox(1, jobId)`. It never drains unrelated backlog. At most two provider calls run concurrently, and at most eight IDs are retained for this latency improvement; healthy queued follow-ups drain as slots free. Existing `availableAt` values and provider delay seconds remain authoritative, including the agent's existing 1,200/15,000 ms schedules. The explicit `/agent` path is unchanged. A full helper, client disconnect, process crash or dispatch failure leaves the original durable intents for normal native maintenance. Its nominal one-minute cadence is a fallback, not a delivery SLO or an exactly-once provider guarantee.

Shutdown drains these post-response calls for at most two seconds before continuing normal teardown. A hung provider is not falsely marked cancelled; its SQL dispatch lease can expire for another maintenance instance. Logs expose only finite categories (`outbox-pending`, `dispatch-failed`, `shutdown-timeout`), never raw provider errors. Worker claims/publication continue to enforce permissions, source snapshots, leases, fences, retry limits and stable dispatch identities.

The optional runtime `dispatchReadiness()` observes persisted failed pending/dispatching intents for nonterminal jobs. The App returns it through `executionReadiness()`, authenticated `/api/capabilities.execution`, and the `x-studio-execution-state` health header. An unresolved failed intent reports `degraded` with reason `outbox-dispatch-pending`; publication or cancellation clears that condition. `configured` still carries `verified: false` and does not certify delivery or execution. Hosting can expose this state while SQL-backed authoring remains ready.
