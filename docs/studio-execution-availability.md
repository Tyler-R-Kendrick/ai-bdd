# Authoring availability during dispatch outages

A persisted job that cannot reach its queue provider must remain queued without preventing authentication, manual document editing, or integration-independent previews. A successful application health check does not prove that queued execution can run.

`OutboxDispatchPendingError` identifies one specific recoverable boundary: an external dispatcher failed, and the coordinator successfully persisted the pending intent and retry backoff. The error contains a fixed code and count, with no raw provider detail. `createApp` catches only this type during startup recovery. SQL/schema errors and domain `HttpError` authorization failures continue to reject startup.

The provider call and its SQL receipt write have separate error boundaries. A database failure while saving a successful dispatch receipt is a storage failure; it is not converted into provider degradation. The intent/lease remains available for bounded replay using its stable dispatch identity. No dispatch receipt, job completion, or output is fabricated.

The optional runtime `dispatchReadiness()` observes failed pending/dispatching intents for nonterminal jobs in SQL. The app returns this through `executionReadiness()`, exposes it as authenticated `/api/capabilities.execution`, and includes its state in the `x-studio-execution-state` health response header. It reports `degraded` with reason `outbox-dispatch-pending` when a failed dispatch remains unresolved. Publication or cancellation removes that condition. `configured` always carries `verified: false`; it does not certify queue delivery, worker execution, or external side effects. The hosting composition can include the returned marker under its execution service while retaining SQL-backed authoring readiness.

Cloud composition selects `createApp(settings, { startupDispatchLimit: 0 })`: startup reconciles durable SQL intents/leases and skips external publication entirely. A slow or nonresponding provider therefore cannot hold manual authoring startup. An unspecified option retains standalone/local startup behavior; a positive option bounds each startup dispatch pass. Maintenance and explicit recovery retain their own budgets, receive typed dispatch failures, and retry according to the existing SQL outbox/backoff policy. Startup handling does not modify job snapshots, leases, fences, source checks, permissions, retry limits, or provider idempotency identities.
