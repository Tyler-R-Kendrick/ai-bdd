# Inline investigation records

Design and regular documents have two typed, canonical blocks: `investigationCard` contains the persisted investigation UUID; `investigationView` contains that UUID and the published native view ID. Both use `attrs.data`. The server, editor, restricted MD/MDX importer, canonical anchor normalizer, and client share the investigation schemas. The source stores identities, never a second authored dataset claiming to be published evidence.

`validateInvestigationReferences` is the canonical Store content-reference hook. It runs in the project transaction for authored documents, imported source, machine/MCP proposals and incoming Yjs updates. A request card belongs only to the investigation's actual source artifact. A native view requires the same project, completed status, exact result SHA-256, schema-valid published result and an existing native view ID. Only the source artifact or the record's actual published child can embed that view. Other artifacts in the same project cannot insert it by guessing IDs. Every already attached, non-withdrawn request retains exactly one card with its stable anchor; moving that same card is allowed. A proposed request must be explicitly withdrawn before its card can be removed. Queued, running, and completed request cards cannot be removed by generic source or Yjs edits. Lookup count, source depth/node count and aggregate UTF-8 result bytes are bounded.

The NodeView fetches the authenticated investigation API, independently checks the parent/child relationship for its current artifact, identifies actual request status/source revision/commit, and reuses the investigation workflow's native view component. Table/chart data, persisted selections, and selection-based decision controls come from that component and its authenticated APIs. Read-only document users receive read-only controls. `DocumentEditor.onInvestigations(id)` opens the application's actual investigation panel; published child navigation uses its stable artifact ID. Missing, invalid and unavailable records show explicit errors instead of invented data.

Restricted Markdown and MDX preserve UUID/view identity and the request-card anchor using a fixed literal JSON envelope (`{id,data}`); no authored code is evaluated. Word and the editor's static HTML representation export readable identity references; they do not claim to embed a live external dataset or interactive selection history. Full investigation records and selections belong to the investigation export workflow.

`tests/investigation-document.test.ts` checks the shared source/editor schemas, invalid attributes, canonical IDs, restricted Markdown/MDX identity roundtrip, readable Word/HTML node representation and lookup bounds. `tests/investigation-document-cloud.test.ts` uses the actual MachineService pairing protocol and InvestigationService schema/leases/completion against SQLite and PostgreSQL. Its ten SQL cases verify actual child native-view publication, parent card/view acceptance, rejection of arbitrary IDs and sibling/cross-project source, create/import/MCP-shaped document validation, incoming Yjs rollback, unchanged source/revision history after rejection, rejection of a tampered result hash, stable card identity across MDX rewrites/moves, explicit withdrawal before removal, and retention during queued/running/completed execution. This is storage/lease/source acceptance evidence; the local execution agent, native UI browser controls, final application wiring and screenshots are covered by their owning workflow rather than inferred from these tests.
